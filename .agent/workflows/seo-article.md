# SEO記事作成ワークフロー

このワークフローはPhase0〜5で構成される（Phase0は任意実行）。各Phaseは順番に実行し、ゲート条件を満たしてから次に進む。
各Phaseの詳細手順はSkillsとして定義されている。エージェントはPhase実行時に対応するSkillを自動で読み込む。

## 実行原則
- Phase間でユーザー承認待ちは挟まない。ゲート判定はエージェントが実行し、欠損入力や実行不能時のみユーザーに確認する。
- 可能な限り、手作業入力ではなくスクリプトで再現可能な形でデータ取得・検証を行う。
- リライト着手前は、`wp_markdown_export/posts/{slug}/index.md`、公開URL一覧CSV、`git log` の `rewrite:` / `new:` コミットを確認し、すでに作成・リライト済みの記事を不用意に再実行しない。

## 入力情報
ユーザーから以下4項目を受け取る（必須）。
- {target_keyword} = ターゲットキーワード
- {article_purpose} = 記事の目的（リード獲得/信頼性構築/サービス認知/教育コンテンツのいずれか）
- {mode} = 実行モード（`new`/`rewrite` または `新規`/`リライト`）
- {base_article_html_or_url} = 元記事URLまたはHTML（`mode=new` の場合は `なし` で可）

追加の任意入力（ある場合のみ使用）:
- {context_injection} = 人間性の注入コンテキスト
- {gsc_csv_path} = Search ConsoleエクスポートCSVのパス（ある場合はPhase1で優先参照）
- {gsc_property} = Search Consoleプロパティ（例: `https://gaikoku-jinzai.tcj-education.com/`）
- {gsc_service_account_json} = サービスアカウントJSONパス
- {gsc_start_date}/{gsc_end_date} = GSC取得期間（`YYYY-MM-DD`）

入力不足時（空起動を含む）は記事執筆を開始せず、必ず以下の文面で返す。

対策KW：
この記事の目的：
モード（新規 or リライト）
元記事のURL：

4項目すべてが入っていないと、記事執筆を開始できません。
（新規の場合、元記事のURLは「なし」でOK）

## Phase0：データ準備（GSC任意自動取得）
以下の優先順位でPhase1に渡す `gsc_csv_path` を決定する。

1. ユーザー入力の `{gsc_csv_path}` がある場合はそれを採用
2. `{gsc_property}` と `{gsc_service_account_json}` がある場合は `scripts/export_gsc_api_csv.py` を実行して自動生成
3. どちらもない場合はGSCなしで続行

推奨出力先：
- `data/gsc/gsc_{YYYY-MM-DD}_{YYYY-MM-DD}.csv`

**ゲート条件**：
- Phase1開始時点で、`gsc_csv_path` が解決済み（または「未使用理由」を1行で明記）であること

## Phase1：入力受付＋検索意図分析
seo-phase1-intentスキルの手順に従い、以下を出力する。
- 検索意図4要素の分析（各要素の「記事での扱い方」含む）
- 記事の本軸（解決手順 or 事実）の決定
- ゴールシナリオ2パターン
- `gsc_csv_path` がある場合は、対象KWの既存実績（主要クエリ、表示回数、CTR、平均掲載順位）を追加で出力し、検索意図分析に反映する
- `mode=rewrite` の場合は、上記に加えて既存記事の精密診断を出力する（不足検索意図、情報鮮度、構成上の欠落、内部リンクの不足箇所）。

**ゲート条件**：上記3点がすべて出力されるまでPhase2に進めない。`mode=rewrite` の場合は既存記事の精密診断も必須。

## Phase2：競合調査＋ギャップ分析
seo-phase2-competitorスキルの手順に従い、以下を出力する。
- PAA質問の4分類
- 関連検索キーワードの優先順位
- 上位5サイトの個別分析（1サイトずつ順番に。まとめて処理しない）
- 検索意図充足度スコアリング
- 共通トピック一覧、差別化トピック一覧
- ギャップ分析
- 差別化の軸（1行）

**ゲート条件**：上記すべてが出力されるまでPhase3に進めない。

## Phase3：戦略・構成設計
seo-phase3-strategyスキルの手順に従い、以下を出力する。
- ペルソナ定義（BtoBの場合は担当者＋決裁者の2名）
- 構成案（全H2/H3/H4と使用パーツ指定＋カスタマージャーニーフェーズ指定）
- 自社USP配置計画（3つ以上のUSPと配置箇所）
- 1次情報・図表の実装計画（4分類）
- 記事全体の想定総文字数
- 本文プレーンテキスト目標文字数（目安と下限根拠）
- Internal Link Plan（主クラスター、候補リンク、配置セクション、採用理由）
- Claim-Evidence Map（主要主張5件以上と出典・配置見出しの紐付け）
- **CTA選定**：`references/cta-wp-reference.md` を参照し、このペルソナ・記事目的・読者のCVSフェーズから「最もCVしやすいネクストアクション」を判断し以下3種を選定する（全て同じURLでなくてよい）。
  - **CTA-A**（リード文直後）：「情報収集中」の読者に適したWPダウンロード
  - **CTA-B**（本文中盤）：「解決策を調べくらべにきた」段階に適した資料請求またはWP
  - **CTA-C**（記事末尾）：「検討期」に入った読者向けのお問い合わせ
  - 各CTAにつき「URL」「キャッチコピー（1行）」「選定理由（1行）」を明記する

**ゲート条件**：上記すべてが出力されるまでPhase4に進めない。


## Phase4：完全執筆（HTML出力）
seo-phase4-writingスキルの手順に従い、以下を出力する。
- タイトル（32文字前後）とメタディスクリプション（120文字前後）
- 記事全文（HTML形式）
- **CTAが記事内に3箇所配置**（Phase3で選定したCTA-A/B/Cを必ず使用）
  - CTA-A：リード文直後（リード文の直後に配置）
  - CTA-B：本文中盤（全体の40～60％位置が目安）
  - CTA-C：記事末尾（FAQ直後またはまとめの後）
- FAQが5問以上
- 1,000文字ごとに1つ以上の視覚要素
- Internal Link Planに基づく内部リンクカード（厳格クラスタ制約、最大3件）
- 内部リンクカード画像は遷移先記事から自動解決し、プレースホルダー画像を残さない
- WordPress互換のため、投稿本文に`<style>`/`<head>`を含めない（内部リンクカードCSSは共通CSS管理）
- `references/html-template.html` のデザインパーツ準拠（テーマ依存クラス禁止、見出しインラインスタイル必須）
- Phase3の本文プレーンテキスト目標文字数に対する自己チェック結果
- Claim-Evidence Mapで定義した主要主張の反映状況（主張欠落・出典欠落の有無）

**ゲート条件**：上記すべてが揃うまでPhase5に進めない。writing-rulesに違反する箇所がないこと。

## Phase5：検証・最終出力
seo-phase5-validationスキルの手順に従い、以下をチェックする。
- SEO要件チェック
- LLMO対策チェック
- Writing Rulesチェック（.agent/rules/writing-rules.mdに準拠）
- E-E-A-Tスコアカード評価（合計15点以上で合格）
- コンテンツ品質チェック
- 内部リンク妥当性チェック（件数、クラスター整合、許可URL）
- デザインテンプレ準拠チェック（WRAPPER・見出し・禁止クラス・内部リンクカードDOM）
- 空虚長文排除チェック（抽象反復・一般論の水増し検知）
- 根拠トレーサビリティチェック（主要主張5件以上が出典と一致）

すべて合格後、最終出力する。
- 完成版HTML
- タイトルとメタディスクリプション（プレーンテキスト）
- 画像プレースホルダー一覧
- 公開後改善タスク（14日後/30日後に確認するGSC指標と対応アクション）
- プロジェクトの進捗管理表に完了ステータスを追記・更新済み

出力後、プロジェクトの進捗管理表（優先度レポートや履歴ファイル）に完了ステータスを追記・更新する。

## Git コミット（最終ステップ・省略禁止）

最終出力後、以下のコマンドでリライト/新規作成の履歴をコミットする。

```bash
# 出力ファイルをステージング（スラッグはoutputファイル名から取得）
git add output/{slug}.html

# コミット（mode に応じてプレフィックスを変える）
# mode=rewrite の場合:
git commit -m "rewrite: {slug} — KW: {target_keyword} ({YYYY-MM-DD})"

# mode=new の場合:
git commit -m "new: {slug} — KW: {target_keyword} ({YYYY-MM-DD})"
```

**コミットメッセージ規則**
- `{slug}` = outputファイルのHTMLファイル名（拡張子なし）
- `{target_keyword}` = 対策KW
- `{YYYY-MM-DD}` = 実行日（現地時間）

## WordPress 下書き保存（最終ステップ）

Gitコミット完了後、以下のルールでWordPressへの送信処理を行う。

- **`mode=new`（新規作成）の場合:**
  エージェントが自動で下書き保存を実行する。
  ```bash
  python scripts/wp_post.py output/{slug}.html --slug "{slug}" --title "{タイトル}" --yes
  ```

- **`mode=rewrite`（リライト）の場合:**
  **エージェントは自動実行してはいけない。**
  「完成ファイルを出力・Gitコミットまで完了しました。内容を確認し、問題なければ以下のコマンドでWordPressへ下書き保存してください。」というメッセージとともに、実行するコマンドを案内して終了する。
  ```bash
  # WP側で該当記事の既存IDがわかる場合は --post-id {ID} を付けると確実です
  python scripts/wp_post.py output/{slug}.html
  ```

これらを以て、すべての作業を完了とする。メタコメント（「以上です」「修正があれば」等）は一切付けない。
